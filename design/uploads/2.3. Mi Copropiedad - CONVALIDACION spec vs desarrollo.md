## Variable: un administrador con VARIAS propiedades (multi-PH)

> El dueno pidio validar esta faceta: un administrador no gestiona una sola copropiedad, sino varias. Conclusion: **la plataforma ya lo soporta a nivel de identidad y datos; el modulo 2.3 opera siempre sobre la copropiedad ACTIVA y el cambio entre PH vive en Capa 1**, no dentro de 2.3.

**Que dice la spec:**
- La spec 2.3 esta redactada para **una sola copropiedad** ("la copropiedad activa"). No define seleccion ni gestion de multiples PH.
- El concepto multi-PH es de **Capa 1 - Organizacion** (empresa administradora): [[1.1 Panel Consolidado]] (panel de todas las PH), Calendario multi-PH (1.2), Equipo de la organizacion (1.3), Reportes cruzados (1.4), Transferencia de custodia (1.5). La spec 2.3 ya nombra al actor "Colaborador de la organizacion".

**Realidad en codigo (verificada):**
- **Modelo de datos:** una `persona` puede pertenecer a varios `tenants` (relacion N:M via `usuarios_tenant`). No hay atadura 1:1 usuario-copropiedad.
- **Auth multi-PH:** el login devuelve `availableTenants` (lista de copropiedades del usuario con su rol). `POST /connect/switch-tenant` **reemite el JWT con otro `tenant_id`** validando que el usuario tenga acceso. `GET /connect/me` lista las copropiedades accesibles. Existe la funcion DB `get_tenants_for_persona`.
- **Aislamiento:** cada request se scopea al `tenant_id` del JWT; **RLS** garantiza que solo se ven datos de la PH activa.
- **UI:** en **Capa 1 Panel Consolidado** se listan las PH con su indicador de salud; el boton "Ir a dashboard" llama `switch-tenant`, guarda el nuevo JWT en `sessionStorage` y entra a esa PH. En el header de cliente existe un indicador de "Copropiedad activa" pero **esta oculto** (`display:none`). **2.3 no tiene selector de copropiedad propio.**

**Delta / recomendaciones para desarrollo:**
- [x] **Selector de copropiedad activa visible** en el shell de cliente -> **HECHO (commit 8c3ec78, 2026-05-27).** `CopropiedadSwitcher` en el panel del sidebar: tarjeta con la PH activa + modal-galeria (logo + nombre + rol) que cambia con `switch-tenant` + recarga. Incluyo fix de login multi-PH (JWT scopeado) y mini-migracion para que `get_tenants_for_persona` devuelva el `logo_url`.
- [ ] **Contexto de PH explicito** en toda accion del agente/MCP (siguiente seccion): no depender de un unico JWT "activo" mutable cuando se opera sobre varias PH en una misma conversacion.
- [ ] Confirmar en 2.3 que el resumen/encabezado deja claro **sobre que PH** se esta configurando (evitar editar la PH equivocada al venir de un switch).
- Nota: la faceta NO es un faltante de 2.3 en si; es una capacidad de Capa 1 que 2.3 consume via el `tenant_id` del JWT. Lo unico ausente es la **comodidad de cambio dentro del flujo de cliente** y el **scoping explicito para el agente**.

## Nueva capa: MCP para consulta y creacion de datos (futuro agente)

> Requerimiento nuevo del dueno: anadir una **capa MCP** que permita **consultar y crear/configurar** datos de la copropiedad, como base para una herramienta tipo **agente** que configure la PH conversacionalmente. **Hoy NO existe** ningun servidor MCP ni tools sobre el dominio 2.3 - es trabajo nuevo. Esta seccion lo deja especificado para la sesion de desarrollo.

**Objetivo:** exponer las capacidades de Mi Copropiedad como **herramientas MCP** (tools) para que un agente pueda leer el estado y ejecutar altas/configuracion (identidad, distribucion, gobierno, equipo, servicios, zonas, equipos), reutilizando la logica ya existente.

**Mapeo de tools propuesto (1:1 sobre `IMiCopropiedadService`):**

| Tipo | Tool (sugerido) | Respaldo existente |
|---|---|---|
| Consulta | `micopropiedad.resumen` | `GET /resumen` |
| Consulta | `micopropiedad.listar_unidades` / `obtener_unidad` | `GET /unidades`, `/unidades/{id}` |
| Consulta | `micopropiedad.listar_{torres,tipos,coeficientes,consejo,comites,equipo,contratos,zonas,equipos}` | endpoints GET respectivos |
| Creacion | `micopropiedad.actualizar_identidad` | `PUT /identidad` |
| Creacion | `micopropiedad.crear_torre` / `crear_unidad` / `eliminar_*` | endpoints POST/DELETE |
| Creacion | `micopropiedad.generar_unidades` (con dry-run) | `POST /unidades/generar` |
| Creacion | `micopropiedad.importar_csv` (con validacion previa) | `POST /unidades/importar-csv` |
| Creacion | `micopropiedad.set_coeficiente_unidad` | `PUT /unidades/{id}/coeficientes` |
| Creacion | `micopropiedad.gobierno_*` / `equipo_*` / `servicios_*` / `zonas_*` / `equipos_*` | endpoints POST respectivos |

**Consideraciones de diseno (obligatorias para desarrollo):**
- [ ] **Capa delgada sobre el servicio:** el MCP debe llamar a `IMiCopropiedadService`, **no** reimplementar logica. El servicio ya valida suma de coeficientes, transaccionalidad del import/generador y duplicados; los **records de `Dtos.cs` son el contrato natural** de inputs de cada tool.
- [ ] **Tenant-scoping explicito por llamada:** cada tool recibe/resuelve el `tenant_id` objetivo y se ejecuta bajo `ITenantContext` + RLS. Imprescindible para el caso multi-PH (un agente operando sobre varias propiedades).
- [ ] **Autorizacion por rol:** las tools de escritura deben respetar la matriz de permisos del usuario que opera el agente. **Ligado al hallazgo P0** de [[0.0.1. LISTA DE CHEQUEO - pendientes de implementacion]] (hoy no hay enforcement por rol): el agente **no puede tener mas permisos** que el usuario. Resolver primero ese fix de autorizacion.
- [ ] **Confirmacion / dry-run en escrituras de impacto:** generar unidades, importar CSV y cambiar coeficientes deben ofrecer **vista previa** y confirmacion explicita antes de aplicar (mismo principio del generador actual).
- [ ] **Auditoria:** toda accion del agente registra autor = agente + usuario que lo invoca. Se apoya en la **bitacora pendiente** (RN-06) que tambien hay que construir.
- [ ] **No confundir con el MCP/canal conversacional de WhatsApp** (Infra IA de Capa 2): aquello es el canal de mensajeria; esta capa es un **tool-layer de dominio** sobre 2.3 (y replicable a otros modulos).
- [ ] **Idempotencia y errores tipados:** devolver errores estructurados (los mismos `InvalidOperationException` -> 400 que ya maneja el controller) para que el agente pueda reintentar/corregir.

**Estado:** no implementado. Recomendacion: arrancar por las **tools de consulta** (bajo riesgo) y, en paralelo, cerrar el fix de autorizacion por rol antes de habilitar las **tools de creacion**.
