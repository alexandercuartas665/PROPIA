## 1. Descripción general

El módulo de Tareas y Proyectos es el **eje operativo central** de la copropiedad. Cualquier módulo de PropIA puede generar tareas aquí — desde la ejecución interna de una PQRSD hasta el cumplimiento de compromisos de asamblea, pasando por los planes de mantenimiento preventivo y las iniciativas propias de la administración.

No es una lista de pendientes. Es un sistema de gestión operativa completo con jerarquía de trabajo, trazabilidad auditada, campos personalizados por proyecto, cuatro vistas de seguimiento y reportes de gestión para el consejo.

**Principios de diseño que rigen este módulo:**

- **Eje central, no módulo aislado** — cualquier módulo puede generar tareas con vínculo bidireccional navegable
- **Una entidad, múltiples niveles** — proyectos y tareas son la misma entidad jerárquica; la complejidad la define el usuario, no el sistema
- **Trazabilidad auditada completa** — cada acción queda registrada en historial append-only con actor, timestamp y contexto
- **Configurabilidad de estados y campos** — cada copropiedad adapta el módulo a su operación sin perder coherencia de plataforma
- **IA como canal de entrada** — el agente de WhatsApp puede crear tareas simples sin que el usuario entre a la plataforma
- **Diseño de primer nivel** — la vista de lista, el tablero Kanban, el Gantt y la ficha de tarea son interfaces extremadamente limpias, funcionales y visualmente atractivas

## 2. Actores

| Actor | Descripción | Acceso en este módulo |
|-------|-------------|----------------------|
| **Administrador** | Gestión completa — crea, asigna, edita, cierra y elimina tareas y proyectos. Configura estados, etiquetas y campos personalizados | Lectura y escritura total |
| **Consejero** | Consulta el estado de proyectos activos y sus indicadores. No puede crear ni editar tareas | Lectura — vista resumen de proyectos |
| **Personal de la copropiedad** | Accede a las tareas donde es responsable o colaborador. Puede agregar comentarios, adjuntos y actualizar estado | Lectura + escritura acotada a sus tareas |
| **Proveedor externo** | Accede a tareas asignadas a su empresa. Puede registrar avance, adjuntar soportes y comentar | Lectura + escritura acotada a sus tareas |
| **Rol con permiso delegado** | Cualquier rol al que el Administrador otorgue acceso al módulo | Según configuración en 2.5 |
| **Agente IA (WhatsApp)** | Crea tareas simples en nombre de un usuario autenticado | Creación con campos mínimos — origen registrado |
| **Super Admin A&D GROUP** | Solo acceso de soporte por impersonación | Excepcional |

## 3. Modelo de entidad — Jerarquía de trabajo

El módulo maneja **una sola entidad** (`tarea`) con jerarquía autorreferencial mediante `padre_id`:

```
Proyecto (tarea raíz — sin padre_id)
├── Tarea (padre_id = Proyecto)
│   ├── Subtarea (padre_id = Tarea)
│   └── Subtarea (padre_id = Tarea)
└── Tarea (padre_id = Proyecto)

Tarea simple (sin padre_id, sin hijos)
```

| Concepto | Definición en PropIA |
|----------|---------------------|
| **Proyecto** | Tarea raíz sin `padre_id`. Tiene vista Gantt, progreso calculado y panel de indicadores |
| **Tarea** | Entidad de trabajo con o sin padre. Tiene ficha completa, responsable, fechas, campos personalizados y trazabilidad |
| **Subtarea** | Tarea hija de otra tarea. Es una tarea completa — con responsable propio, fechas, campos personalizados, comentarios y trazabilidad independiente |

> **Profundidad recomendada:** La plataforma soporta jerarquía ilimitada, pero la UI está optimizada para máximo 3 niveles (Proyecto → Tarea → Subtarea). El Gantt solo renderiza los dos primeros niveles.

## 4. Estados

Los estados son **configurables por la copropiedad**. Existe un conjunto base predeterminado que puede ser renombrado, reordenado y ampliado. Los estados `COMPLETADA` y `CANCELADA` son terminales, no configurables y no eliminables.

### Estados base predeterminados

| # | Estado | Descripción | Terminal |
|---|--------|-------------|---------|
| 1 | **Pendiente** | Creada, sin iniciar | No |
| 2 | **En progreso** | Trabajo iniciado | No |
| 3 | **En revisión** | Esperando aprobación o validación | No |
| 4 | **Bloqueada** | Impedimento activo registrado | No |
| 5 | **Completada** | Cerrada exitosamente | **Sí** |
| 6 | **Cancelada** | Descartada con razón registrada | **Sí** |

### Reglas de configuración de estados

| Acción | ¿Permitida? |
|--------|------------|
| Renombrar estados base (excepto Completada y Cancelada) | ✅ |
| Agregar estados personalizados intermedios | ✅ |
| Reordenar estados en el flujo | ✅ |
| Eliminar estados base | ❌ |
| Eliminar un estado con tareas activas | ❌ — debe reasignar primero |
| Modificar nombre de Completada o Cancelada | ❌ |

## 6. Campos

### 6.1 Campos del sistema (fijos)

| Campo | Tipo | Descripción |
|-------|------|-------------|
| `numero_tarea` | Código visible | `T-{AÑO}-{SEQ}` por copropiedad — generado automáticamente con lock de escritura |
| `titulo` | Texto corto | Obligatorio |
| `descripcion` | Texto largo | Opcional |
| `estado_id` | FK → `tarea_estado` | Obligatorio — Pendiente por defecto |
| `prioridad` | ENUM | Normal por defecto |
| `asignado_a` | FK → `persona` | Responsable principal — opcional |
| `fecha_inicio` | Date | Opcional — informativa |
| `fecha_vencimiento` | Date | Opcional — activa semáforo y alertas |
| `fecha_completada` | Timestamptz | Registrada automáticamente al llegar a estado Completada |
| `padre_id` | UUID autorreferencial | NULL = tarea raíz (proyecto o tarea simple) |
| `origen` | ENUM | `MANUAL` / `WHATSAPP_IA` / `MODULO_EXTERNO` |
| `creado_por` | FK → `usuario` | Automático |
| `copropiedad_id` | FK → `copropiedad` | Obligatorio — multi-tenant |

### 6.2 Campos personalizados

Cada copropiedad puede definir campos personalizados a dos niveles:

| Nivel | Alcance |
|-------|---------|
| **Global** | Disponibles en todas las tareas de la copropiedad |
| **Por proyecto** | Solo disponibles en las tareas hijas de ese proyecto |

Los campos personalizados se heredan en todas las subtareas del proyecto donde se definen.

#### Tipos de campo personalizados disponibles

| Tipo | Ejemplo de uso |
|------|---------------|
| **Texto corto** | Número de orden de compra |
| **Texto largo** | Observaciones técnicas |
| **Número** | Área afectada en m² |
| **Moneda** | Valor del contrato, presupuesto estimado |
| **Fecha** | Fecha planeada, fecha de inspección |
| **Fecha + hora** | Cita con proveedor |
| **Selección simple** | Tipo de intervención |
| **Selección múltiple** | Zonas afectadas |
| **Checkbox** | ¿Requiere cotización? |
| **URL** | Enlace a cotización externa |
| **Persona** | Supervisor externo |
| **Lista de verificación** | Pasos previos a una inspección, ítems de entrega |

## 7. Etiquetas

Las etiquetas son **libres y configurables por la copropiedad**.

| Característica | Detalle |
|---------------|---------|
| Creación | El administrador crea etiquetas con nombre y color personalizado |
| Alcance | Globales para toda la copropiedad |
| Asignación | Múltiples etiquetas por tarea |
| Uso | Filtros, agrupaciones y reportes |
| Sin catálogo predefinido | Cada copropiedad construye el suyo |

**Ejemplos típicos:** `Proveedor externo`, `Fachada`, `Zona húmeda`, `Consejo`, `Urgente`, `Garantía`

## 8. Dependencias entre tareas

Se soporta un único tipo de dependencia: **Finalizar → Iniciar**.

| Concepto | Detalle |
|----------|---------|
| **Tipo** | Finalizar → Iniciar: la tarea B no puede iniciar hasta que la tarea A esté en estado Completada |
| **Alcance** | Aplica entre tareas del mismo proyecto |
| **Visualización** | Líneas de dependencia en la vista Gantt |
| **Bloqueo** | El sistema advierte si se intenta marcar como En progreso una tarea con dependencia no resuelta — no bloquea automáticamente, advierte |

## 9. Colaboradores

| Rol | Descripción |
|-----|-------------|
| **Responsable principal** (`asignado_a`) | Un solo actor — rinde cuentas por la tarea. Recibe alertas de vencimiento |
| **Colaboradores** (`tarea_colaborador[]`) | Múltiples actores — participan sin rendir cuentas. Reciben notificaciones de comentarios y cambios de estado |

Los colaboradores se seleccionan del Directorio (personas y empresas vinculadas a la copropiedad).

## 10. Vistas

| Vista | Descripción | Disponible para |
|-------|-------------|----------------|
| **Lista** | Tabla con filas por tarea, columnas configurables, filtros, búsqueda y bulk actions. Vista predeterminada | Todos los niveles |
| **Tablero Kanban** | Columnas por estado, tarjetas drag & drop. Al mover una tarjeta, el cambio de estado se registra en trazabilidad | Todos los niveles |

## 11. Ficha de tarea — Modos de apertura

Cada tarea tiene dos modos de visualización:

| Modo | Descripción | Cuándo se usa |
|------|-------------|--------------|
| **Drawer lateral** | Panel deslizante sin abandonar la vista activa | Edición rápida de campos, cambio de estado, comentario rápido |

La página completa es la **ficha viva de la tarea** — coherente con el patrón de navegación por entidad establecido en toda la Capa 2.

## 13. Vínculo bidireccional con módulos origen

Cuando una tarea se genera desde otro módulo, queda vinculada con referencia navegable en ambos lados.

| Módulo origen | Lo que genera | Vínculo en la tarea | Vínculo en el origen |
|---------------|--------------|--------------------|--------------------|
| **2.8 — Asambleas** | Compromiso del acta | "Generada desde acta: Asamblea Ordinaria Mar 2026" | "Tarea de seguimiento: T-2026-0012" |
| **2.9 — PQRSD** | Ejecución interna de expediente | "Generada desde expediente: PQRS-2026-001-0042" | "Tarea de ejecución: T-2026-0015" |
| **2.11 — Mantenimiento** | Mantenimiento preventivo o correctivo | "Generada desde plan de mantenimiento: Bomba principal" | "Tarea de ejecución: T-2026-0018" |

**Comportamiento del vínculo:**
- El vínculo es navegable con un clic — lleva al objeto origen en su módulo
- La tarea hereda automáticamente: título sugerido, descripción de contexto y prioridad recomendada según el módulo
- El cierre de la tarea **no** cierra automáticamente el objeto origen — son ciclos independientes
- La tarea generada desde 2.9 es **invisible para el radicador** — es de gestión interna

## 14. Creación desde WhatsApp vía agente IA

El agente conversacional de PropIA en WhatsApp puede crear tareas simples para usuarios autenticados.

### Campos mínimos requeridos para crear desde WhatsApp

| Campo | Comportamiento |
|-------|---------------|
| `titulo` | Extraído del mensaje por el agente IA |
| `asignado_a` | El agente resuelve el nombre desde el Directorio. Si no puede resolverlo, la tarea se crea sin responsable y se notifica al administrador |
| `fecha_vencimiento` | Extraída si se menciona una fecha. Si no, queda vacía |
| `origen` | `WHATSAPP_IA` — registrado automáticamente en trazabilidad |
| `estado` | `PENDIENTE` — siempre |
| `prioridad` | `NORMAL` — por defecto |

### Lo que el agente NO puede hacer desde WhatsApp

| Acción | Motivo |
|--------|--------|
| Crear proyectos con subtareas | Requiere estructura visual de la plataforma |
| Asignar campos personalizados | Requiere conocimiento del catálogo del proyecto |
| Establecer dependencias | Requiere selección de tareas existentes |
| Definir colaboradores múltiples | Complejidad de resolución en chat |

La tarea creada llega a la bandeja del administrador con notificación para enriquecerla si lo requiere.

## 15. Trazabilidad auditada

Cada tarea tiene un **hilo de actividad unificado** que mezcla en orden cronológico comentarios manuales y eventos del sistema.

### Tipos de entrada en el hilo

| Tipo | Ejemplo | Editable |
|------|---------|---------|
| **Comentario manual** | Texto libre con menciones @, adjuntos | Sí — por el autor, dentro de ventana configurable |
| **Evento de estado** | "Estado cambiado a En progreso por Juan Pérez" | No — append-only |
| **Cambio de campo** | "Fecha de vencimiento: 15 abr → 22 abr" | No — append-only |
| **Tarea creada desde módulo** | "Generada desde PQRSD #PQRS-2026-001-0042" | No — append-only |
| **Archivo adjunto** | Fotos, PDFs, cotizaciones | No eliminable por otros actores |
| **Cambio de responsable** | "Responsable: Carlos López → María Gómez" | No — append-only |

### Estructura de cada entrada de trazabilidad

| Campo | Descripción |
|-------|-------------|
| `actor_id` | Quién ejecutó la acción (NULL si fue automático) |
| `origen` | `MANUAL` / `SISTEMA` / `MODULO_EXTERNO` / `WHATSAPP_IA` |
| `timestamp` | Fecha y hora exacta (UTC) |
| `campo_modificado` | Qué campo cambió — si aplica |
| `valor_anterior` | Estado previo del campo |
| `valor_nuevo` | Estado posterior del campo |
| `nota` | Texto libre del comentario — si aplica |

> La tabla `tarea_historial` es **append-only a nivel de base de datos** — sin permisos de UPDATE ni DELETE. Ningún actor, incluido el Super Admin, puede borrar una entrada de trazabilidad.

## 17. Progreso de proyectos

El progreso de un proyecto se calcula **automáticamente** — no es un campo manual.

```
% progreso = (subtareas en estado Completada / total de subtareas directas) × 100
```

- Solo cuenta las tareas hijas directas del proyecto (primer nivel)
- Las tareas en estado Cancelada no cuentan en el denominador
- El progreso se muestra como barra visual en la vista Lista y en el panel de indicadores del proyecto
- El porcentaje se recalcula en tiempo real cada vez que una tarea hija cambia de estado

## 18. Reportes e indicadores

Los indicadores se calculan en backend y están disponibles para el administrador, el consejo (vista de solo lectura) y el módulo 2.16 Reportes e Indicadores.

| Indicador | Descripción |
|-----------|-------------|
| **Tareas por estado** | Distribución actual del inventario de tareas activas |
| **Tareas vencidas** | Cantidad y detalle de tareas fuera de plazo |
| **Tareas por responsable** | Carga de trabajo por persona — identifica sobrecargas |
| **Tareas por prioridad** | Distribución urgente / alta / normal / baja |
| **Tareas por módulo origen** | Cuántas vienen de PQRSD, Mantenimiento, Asambleas, creación manual |
| **Proyectos por avance** | % de completitud de cada proyecto activo |
| **Tiempo promedio de cierre** | Desde creación hasta Completada, filtrable por tipo de origen |

### Vista del consejo

El consejo tiene una vista de **solo lectura diferenciada** — sin acceso a la gestión operativa — que muestra:
- Proyectos activos con barra de progreso
- Tareas vencidas por proyecto
- Resumen de indicadores clave del período

## 20. Reglas de negocio

| # | Regla | Detalle |
|---|-------|---------|
| RN-01 | **Número de tarea inmutable** | `T-{AÑO}-{SEQ}` se genera al crear y nunca cambia |
| RN-02 | **Estados Completada y Cancelada son terminales** | No se puede cambiar el estado de una tarea terminal — solo el administrador puede reabrirla con justificación registrada en trazabilidad |
| RN-03 | **Cancelar requiere razón** | El campo razón de cancelación es obligatorio — mínimo 10 caracteres |
| RN-04 | **Progreso de proyecto es automático** | No existe campo de progreso manual. Se calcula siempre a partir del estado de las tareas hijas directas |
| RN-05 | **Eliminar estado con tareas activas no está permitido** | El administrador debe reasignar las tareas a otro estado antes de eliminar |
| RN-06 | **Subtareas son tareas completas** | Tienen responsable propio, fechas, campos personalizados, comentarios y trazabilidad independiente |
| RN-07 | **Dependencia solo entre tareas del mismo proyecto** | No se pueden crear dependencias entre proyectos distintos ni entre tareas sueltas |
| RN-08 | **La tarea de 2.9 es invisible para el radicador** | Nunca se expone en el portal del radicador ni en notificaciones hacia él |
| RN-09 | **El cierre de la tarea no cierra el objeto origen** | La tarea y el objeto que la generó (expediente, compromiso de acta, mantenimiento) son ciclos independientes |
| RN-10 | **Campos personalizados de proyecto se heredan en subtareas** | Las tareas hijas muestran los campos definidos en su proyecto raíz |
| RN-11 | **Tarea desde WhatsApp sin responsable resuelto** | Se crea con `asignado_a = NULL` y se notifica al administrador inmediatamente |
| RN-12 | **La vista del consejo es solo lectura** | Los consejeros no pueden crear, editar ni cambiar estado de ninguna tarea |
| RN-13 | **El semáforo se calcula en backend** | Verde (sin vencer), Amarillo (vence en ≤ 3 días), Rojo (vencida). Nunca en frontend |
| RN-14 | **Trazabilidad no se puede borrar** | Ningún actor puede eliminar entradas del historial — ni el Super Admin |

## 21. Validaciones

| Campo | Validación |
|-------|-----------|
| `titulo` | Obligatorio. Mínimo 3 caracteres. Máximo 200 caracteres |
| `descripcion` | Opcional. Máximo 5.000 caracteres |
| `fecha_vencimiento` | Debe ser igual o posterior a `fecha_inicio` si ambas están definidas |
| `razon_cancelacion` | Obligatoria si el nuevo estado es Cancelada. Mínimo 10 caracteres |
| Campos personalizados obligatorios | Validados según la configuración del campo en `tarea_campo_definicion` |
| Adjuntos | Formatos: jpg, png, pdf, docx, xlsx, mp4. Máximo 10 archivos por comentario. Máximo 25MB por archivo |
| Dependencia circular | El sistema valida que la dependencia no forme un ciclo antes de guardarla |

## 22. Comportamientos automáticos

| Trigger | Comportamiento |
|---------|---------------|
| Tarea creada | Genera `numero_tarea` con lock de escritura · Notifica a responsable y colaboradores · Registra en historial |
| Tarea asignada (sin ser la creación) | Notifica al nuevo responsable · Registra cambio en historial |
| Estado cambiado a Completada | Registra `fecha_completada = now()` · Recalcula progreso del proyecto padre · Notifica a creador y módulo origen · Registra en historial |
| Tarea vence en N días (configurable) | Job nocturno · Envía alerta a responsable |
| Tarea vencida | Job nocturno · Envía alerta a responsable + creador · Cambia semáforo a Rojo |
| Drag & drop en Kanban | Cambia estado · Registra en historial con `origen = SISTEMA` |
| Tarea creada desde módulo externo | Registra `origen = MODULO_EXTERNO` · Almacena vínculo en `tarea_origen` · Hereda contexto mínimo del objeto origen |
| Tarea creada desde WhatsApp | Registra `origen = WHATSAPP_IA` · Si no se resuelve responsable, notifica al administrador |

## 25. Notas para el desarrollador

| Tema | Detalle |
|------|---------|
| **Número de tarea** | Formato: `T-{AÑO}-{SEQ}`. El secuencial es por copropiedad y reinicia en 0001 cada año. Generar con lock de escritura para garantizar unicidad bajo concurrencia |
| **Modelo EAV para campos personalizados** | El patrón Entity-Attribute-Value requiere consultas cuidadosas. Construir una vista materializada o capa de proyección por proyecto para evitar N+1 queries en la vista Lista |
| **Validación de ciclos en dependencias** | Antes de insertar en `tarea_dependencia`, verificar que no se forma un ciclo con DFS (Depth-First Search) sobre el grafo de dependencias del proyecto |
| **Progreso de proyecto** | Calcular en backend al servir el proyecto. No persistir el porcentaje — calcularlo siempre desde el estado actual de las tareas hijas |
| **Historial append-only** | Implementar sin permisos de UPDATE ni DELETE a nivel de BD. Toda acción sobre la tarea debe generar al menos una entrada en `tarea_historial` |
| **Multi-tenant** | Todas las tablas incluyen `copropiedad_id` como FK obligatorio. Nunca ejecutar queries sin filtro por `copropiedad_id` |
| **Almacenamiento de adjuntos** | Bucket por tenant: `/ph/{copropiedad_id}/tareas/{tarea_id}/`. Entregar siempre como URL firmada de tiempo limitado (máximo 1 hora). Nunca exponer la URL de storage directa |
| **Semáforo de vencimiento** | Calcular en backend al servir la lista: Verde = sin vencer, Amarillo = vence en ≤ 3 días, Rojo = vencida. Incluir en la respuesta de la API: `semaforo: 'VERDE' | 'AMARILLO' | 'ROJO'` |
| **Gantt en frontend** | Requiere librería especializada (DHTMLX Gantt, Frappe Gantt o similar). Paginar la carga de tareas en proyectos grandes — no cargar todo el árbol de golpe |
| **Creación desde WhatsApp** | El agente IA debe resolver `asignado_a` buscando en el Directorio por nombre o apodo. Si no puede resolverlo con confianza ≥ 0.85, crear la tarea con `asignado_a = NULL` y notificar al administrador |
| **Campos personalizados heredados** | Al renderizar la ficha de una subtarea, consultar `tarea_campo_definicion` filtrando por `proyecto_id = raíz del árbol` de esa subtarea |
| **Eliminación suave de etiquetas y estados** | Usar `activo = false` — nunca DELETE físico. Las tareas históricas mantienen referencia íntegra |
| **Punto de extensión para T.1** | Dejar endpoint `/api/tareas/{id}/sugerencias-ia` para que en Fase 3 el módulo T.1 pueda inyectar recomendaciones inteligentes sin rediseño |
| **Vista del consejo** | El backend debe evaluar el rol antes de serializar la respuesta — los consejeros nunca reciben datos de trazabilidad interna ni información de actores asignados a tareas de gestión privada |
