## 1. Descripción general

El módulo de Usuarios, Roles y Accesos es el motor de seguridad y permisos de PropIA dentro de cada copropiedad. Gestiona las credenciales de acceso de todos los actores vinculados a la plataforma, define qué puede ver y hacer cada rol, y garantiza que la información de cada copropiedad esté protegida por una matriz de permisos granular y configurable.

No es un módulo de identidad — ese es el Directorio (2.4). Este módulo toma las identidades del Directorio y les otorga, configura o revoca acceso al sistema.

**Principio fundamental:** La identidad vive en el Directorio. El acceso vive aquí. Una persona puede existir en el Directorio sin tener acceso al sistema — y puede tener acceso revocado sin que su identidad desaparezca.

**Principios de diseño que rigen este módulo:**
- Self-service 100% — el Administrador configura roles y accesos sin intervención de A&D GROUP
- Zero-touch operativo — A&D GROUP no toca la configuración de permisos de ningún tenant
- Permisos granulares — control por módulo, por acción y por nivel de dato
- Scope por copropiedad — la configuración de roles es independiente entre copropiedades
- Configurabilidad total — los roles base no se eliminan pero sus permisos son editables
- Recursividad de permisos — cualquier rol con el permiso "Gestionar usuarios y roles" puede ejercerlo

## 2. Actores

| Actor | Descripción | Acceso en este módulo |
|---|---|---|
| Administrador Delegado | Gestiona usuarios, roles y permisos de la copropiedad | Lectura y escritura total |
| Rol con permiso delegado | Cualquier rol al que el Administrador otorgue el permiso "Gestionar usuarios y roles" | Lectura y escritura según permiso |
| Usuario autenticado | Cualquier persona con acceso activo — puede ver su propia sesión | Lectura propia |
| Super Admin A&D GROUP | Solo acceso de soporte por impersonación | Excepcional |

## 3. Estructura del módulo

El módulo se organiza en dos componentes con ubicaciones distintas en la plataforma:

| Componente | Ubicación | Frecuencia de uso |
|---|---|---|
| **Gestión de usuarios** | Módulo 2.5 — menú de navegación principal | Alta — uso frecuente |
| **Configuración de roles y permisos** | Configuración de la copropiedad | Baja — setup inicial y ajustes ocasionales |
| **Acceso directo desde 2.5 a Configuración** | Botón/enlace dentro del módulo 2.5 | Puente entre ambos componentes |

## 5. Flujos principales

### Flujo 1 — Invitar usuario al sistema

```
Administrador abre 2.5
  → Clic en [+ Invitar usuario]
  → Busca persona por nombre, documento o email (fuente: Directorio 2.4)
  → Selecciona persona existente o crea registro mínimo si no existe
  → Asigna rol
  → Sistema genera token de invitación (72 horas de vigencia)
  → Envía invitación por email y/o WhatsApp (vía T.2)
  → Persona recibe invitación → configura método de autenticación
  → Acceso activado → estado cambia a ACTIVO en tab Activos
```

### Flujo 2 — Revocar acceso

```
Administrador selecciona usuario → [Revocar acceso]
  → Confirmación: "¿Seguro que deseas revocar el acceso de [nombre]?"
  → Confirma
  → JWT/sesión invalidada en tiempo real
  → Usuario pasa a tab Inactivos
  → Registro en auditoría
  → Notificación opcional al usuario vía T.2
  → El registro de la persona en el Directorio permanece intacto
```

### Flujo 3 — Crear rol personalizado

```
Administrador va a Configuración → Roles y Permisos
  → [+ Nuevo rol] o [Copiar de otro rol]
  → Si copia: selecciona rol origen → asigna nombre al nuevo rol
  → Si nuevo: nombre + selecciona módulos base a habilitar
  → Configura matriz: por módulo → por acción → nivel de dato
  → Guarda
  → Rol disponible inmediatamente para asignar a usuarios
```

### Flujo 4 — Copiar rol entre copropiedades (vista multi-PH)

```
Administrador en vista de portfolio (Capa 1)
  → Selecciona copropiedad origen → Roles y Permisos
  → Selecciona rol → [Copiar a otra copropiedad]
  → Selecciona copropiedad(s) destino de su portfolio
  → Sistema copia la configuración del rol — no sobrescribe si ya existe un rol con ese nombre
  → Administrador ajusta en la copropiedad destino si necesita variaciones
```

### Flujo 5 — Login y selector de contexto

```
Usuario ingresa credenciales (email/contraseña, magic link, WhatsApp OTP, Google SSO, Microsoft SSO)
  → Autenticación exitosa
  → Si tiene una sola copropiedad: entra directo al Dashboard
  → Si tiene varias: selector de contexto con última visitada destacada
  → Selecciona copropiedad → Dashboard de esa PH
  → Puede cambiar de contexto en cualquier momento desde el menú superior
```

## 6. Catálogo de roles

### Roles base — no eliminables, permisos configurables

| Rol | Descripción | Nivel de acceso por defecto |
|---|---|---|
| **Administrador** | Gestiona la PH operativamente | Acceso completo a todos los módulos de la copropiedad |
| **Consejero** | Miembro del Consejo de Administración | Supervisión — lectura de métricas + acciones limitadas configurables |
| **Propietario** | Titular del inmueble | Portal propio + acciones de titularidad (asamblea, documentos legales, estado de cuenta) |
| **Residente** | Persona que habita la unidad | Portal propio — PQRS, reservas (configurable), estado de cuenta |
| **Operario** | Personal de servicios o mantenimiento | Solo tareas asignadas |

### Roles extendidos — predefinidos, activables, eliminables

| Rol | Descripción | Activo por defecto |
|---|---|---|
| **Coordinador** | Apoyo operativo con acceso amplio — sin permisos financieros completos | ❌ |
| **Contador** | Acceso a módulos financieros — solo lectura por defecto | ❌ |
| **Revisor Fiscal** | Acceso de auditoría — lectura en finanzas y documentos | ❌ |
| **Asistente** | Apoyo administrativo — PQRS, tareas, directorio | ❌ |
| **Vigilante de Seguridad** | Portería, directorio básico, correspondencia | ❌ |
| **Inmobiliaria** | Acceso restringido a unidades bajo su gestión | ❌ |

> Los roles extendidos eliminados pueden restaurarse desde el catálogo base de PropIA.

### Propietario vs Residente — diferencias clave

| Capacidad | Residente | Propietario |
|---|---|---|
| Ver estado de cuenta de su unidad | ✅ | ✅ |
| Registrar pagos | ✅ | ✅ |
| Radicar PQRS | ✅ | ✅ |
| Reservar zonas comunes | ✅ configurable | ✅ configurable |
| Ver documentos de asamblea | ❌ | ✅ |
| Participar / votar en asamblea | ❌ | ✅ |
| Otorgar poder para asamblea | ❌ | ✅ |
| Ver documentos legales de la PH | ❌ | ✅ |
| Recibir notificaciones de cuotas extraordinarias | ❌ | ✅ |

> La configuración de reservas para Propietario y Residente es independiente y la define el Administrador según el manual de convivencia de cada PH.

## 7. Historias de usuario

> **HU-2.5-01**
> *Como administrador, quiero invitar a un usuario al sistema asignándole un rol para que pueda acceder a la plataforma con los permisos correctos.*
>
> **Criterios de aceptación:**
> - Se busca la persona en el Directorio antes de invitar — no se crean identidades paralelas
> - Si la persona no existe en el Directorio se puede crear un registro mínimo desde el flujo de invitación
> - La invitación se envía por email y/o WhatsApp según los datos disponibles
> - El token de invitación expira en 72 horas
> - El estado del usuario aparece como PENDIENTE hasta que acepte la invitación
> - El administrador puede reenviar o cancelar una invitación pendiente

> **HU-2.5-02**
> *Como administrador, quiero revocar el acceso de un usuario para que deje de poder ingresar a la copropiedad en la plataforma.*
>
> **Criterios de aceptación:**
> - La revocación es inmediata — la sesión activa se invalida en tiempo real
> - El registro del usuario pasa al tab Inactivos — no se elimina
> - El historial operativo de la persona (tareas, PQRS, pagos) se conserva intacto
> - La revocación queda registrada en el log de auditoría con usuario, fecha y motivo opcional

> **HU-2.5-03**
> *Como administrador, quiero crear un rol personalizado copiando uno existente para agilizar la configuración de permisos.*
>
> **Criterios de aceptación:**
> - Se puede copiar cualquier rol existente (base, extendido o personalizado)
> - El rol copiado es independiente del original — los cambios no se propagan entre sí
> - El nombre del nuevo rol es editable y no puede repetirse dentro de la copropiedad
> - Los permisos del rol copiado se pueden ajustar antes de guardar

> **HU-2.5-04**
> *Como administrador que gestiona múltiples PHs, quiero copiar la configuración de un rol de una copropiedad a otra para no tener que configurarlo desde cero.*
>
> **Criterios de aceptación:**
> - Solo se puede copiar entre copropiedades del mismo administrador
> - Si ya existe un rol con el mismo nombre en la copropiedad destino, el sistema alerta y pregunta si desea sobreescribir o crear como nuevo
> - La copia es un punto de partida — el administrador puede ajustarla en destino sin afectar el original

> **HU-2.5-05**
> *Como usuario con múltiples copropiedades, quiero ver el selector de contexto al ingresar para elegir a cuál accedo.*
>
> **Criterios de aceptación:**
> - Si tengo una sola copropiedad vinculada, entro directo sin selector
> - Si tengo varias, el selector muestra todas con nombre, rol y última visita
> - La última copropiedad visitada aparece destacada como sugerencia
> - Puedo cambiar de copropiedad en cualquier momento desde el menú superior sin necesidad de cerrar sesión

> **HU-2.5-06**
> *Como administrador, quiero configurar si los residentes y propietarios pueden reservar zonas comunes según el manual de convivencia de mi copropiedad.*
>
> **Criterios de aceptación:**
> - La configuración de reservas es independiente para el rol Residente y el rol Propietario
> - La configuración vive en la matriz de permisos del módulo Reservas de Zonas Comunes
> - El cambio aplica de inmediato para todos los usuarios con ese rol en la copropiedad

## 8. Reglas de negocio

| # | Regla |
|---|---|
| RN-01 | El acceso al sistema es independiente de la existencia en el Directorio. Una persona puede estar en el Directorio sin tener acceso al sistema |
| RN-02 | El acceso siempre se otorga a una persona existente en el Directorio — nunca se crea una credencial sin identidad vinculada |
| RN-03 | Los roles base (Administrador, Consejero, Propietario, Residente, Operario) no se pueden eliminar ni renombrar — solo se puede editar su matriz de permisos |
| RN-04 | Los roles extendidos predefinidos vienen desactivados por defecto — el Administrador los activa según necesidad |
| RN-05 | Los roles extendidos eliminados pueden restaurarse desde el catálogo base de PropIA — la restauración trae la configuración de permisos por defecto |
| RN-06 | Cualquier rol que tenga el permiso "Gestionar usuarios y roles" habilitado puede invitar usuarios, cambiar roles y revocar accesos — independiente de si es un rol base o personalizado |
| RN-07 | La configuración de roles y permisos es por copropiedad — independiente entre PHs del mismo administrador |
| RN-08 | Al revocar acceso, la sesión activa del usuario se invalida en tiempo real. No existe un período de gracia |
| RN-09 | Al inactivar el vínculo de una persona en el Directorio (módulo 2.4), su acceso en 2.5 se revoca automáticamente mediante evento interno |
| RN-10 | Una persona puede tener roles distintos en copropiedades distintas. El rol aplica siempre en el contexto de la copropiedad seleccionada |
| RN-11 | El token de invitación tiene vigencia de 72 horas y es de un solo uso. Al expirar, el administrador puede regenerarlo |
| RN-12 | La copia de rol entre copropiedades solo está disponible entre PHs gestionadas por el mismo administrador dentro de su portfolio |
| RN-13 | La visibilidad de información entre residentes de la misma copropiedad es configurable por el Administrador según el reglamento de la PH — aplica sobre los módulos de Directorio y Comunicaciones |
| RN-14 | El log de auditoría de este módulo es append-only e inalterable — ningún rol puede modificar ni eliminar registros de auditoría |
| RN-15 | Un rol no puede ser eliminado si tiene usuarios activos asignados — el sistema debe alertar y solicitar reasignación previa |
| RN-16 | El 2FA es opcional para todos los roles y obligatorio para Administrador y Super Admin PropIA |

## 9. Validaciones

| Campo / Evento | Validación |
|---|---|
| Invitación a usuario | La persona debe existir o crearse en el Directorio antes de otorgar acceso |
| Nombre de rol | Único dentro de la copropiedad — no puede repetirse |
| Eliminación de rol | Bloqueada si tiene usuarios activos — el sistema lista los usuarios afectados |
| Token de invitación | Un solo uso · expira en 72 horas · se invalida al aceptarse |
| Cambio de rol | No se puede quitar el rol Administrador al último Administrador activo de la copropiedad |
| Permisos "Gestionar usuarios y roles" | No se puede otorgar este permiso a un rol si el actor que lo configura no lo posee él mismo |
| Copia de rol entre PHs | Solo entre copropiedades del mismo administrador — validado contra el portfolio del administrador autenticado |

## 10. Comportamientos automáticos

| Evento | Acción automática |
|---|---|
| Vínculo inactivado en 2.4 | Sesión invalidada en tiempo real + usuario pasa a INACTIVO en 2.5 |
| Token de invitación expirado | Estado cambia a EXPIRADO automáticamente — job horario |
| Invitación aceptada | Estado cambia a ACTIVO + notificación al administrador vía T.2 |
| Rol eliminado con usuarios activos | Bloqueo + alerta con lista de usuarios a reasignar |
| Último Administrador activo | Sistema impide revocar su acceso o cambiar su rol — alerta preventiva |
| Intento fallido de login × 5 | Bloqueo temporal de la cuenta + notificación al usuario vía email/WhatsApp |
| Nuevo acceso desde dispositivo no reconocido | Notificación al usuario vía email o WhatsApp |
| Cierre remoto de sesión | JWT invalidado en tiempo real para el dispositivo seleccionado |
| Inicio de sesión exitoso | Registro en log: IP · dispositivo · canal de autenticación · timestamp |

## 11. Métodos de autenticación

| Método | Perfil principal | Notas |
|---|---|---|
| Email + contraseña | Universal | Método base disponible para todos los roles |
| Magic link (email) | Residentes y propietarios | Reduce fricción — sin contraseña que recordar |
| WhatsApp OTP | Residentes, propietarios, operarios | Canal nativo PropIA — más natural en Colombia |
| Google SSO | Equipos administrativos con Google Workspace | Diferencial para administradoras corporativas |
| Microsoft SSO | Equipos administrativos con Microsoft 365 | Diferencial para administradoras corporativas |

> Un mismo usuario puede tener múltiples métodos de autenticación vinculados — gestionables desde T.6 Perfil y Preferencias.

## 12. Seguridad de sesión

| Control | Configuración |
|---|---|
| Expiración de sesión inactiva | 30 minutos para roles administrativos · 7 días para Residente y Propietario |
| Refresh token | Renovación silenciosa mientras hay actividad activa |
| 2FA | Opcional para todos · obligatorio para Administrador y Super Admin PropIA |
| Intentos fallidos | Bloqueo temporal tras 5 intentos · desbloqueo por email o WhatsApp |
| Sesiones concurrentes | Permitidas · listado de dispositivos activos visible para el usuario |
| Cierre remoto de sesión | El usuario puede cerrar sesiones desde otros dispositivos — desde T.6 |
| Revocación inmediata | Al inactivar vínculo en 2.4 la sesión se invalida en tiempo real |
| Log de accesos | Registro de IP · dispositivo · canal · timestamp por cada login |

## 15. Notas para el desarrollador

- La evaluación de permisos se ejecuta siempre en el backend — nunca confiar en el frontend para filtrar acceso. El frontend adapta la UI según los permisos recibidos del backend, pero el backend siempre valida antes de ejecutar cualquier operación
- La tabla `rol_permiso` es la fuente de verdad de lo que puede hacer cada rol. Se debe cachear por sesión con invalidación ante cualquier cambio en la matriz del rol
- La invalidación de sesión en tiempo real al revocar acceso requiere una estrategia de blacklist de JWT o uso de tokens de corta duración con refresh. Recomendado: access token de 15 minutos + refresh token con blacklist en Redis
- El token de invitación se genera con `crypto.randomBytes(64).toString('hex')` — nunca con UUIDs predecibles
- La tabla `acceso_auditoria` es append-only — implementar sin permisos de UPDATE ni DELETE a nivel de BD (políticas RLS en Supabase)
- El job de expiración de invitaciones se ejecuta cada hora — cambia `estado = 'EXPIRADA'` donde `expira_at < now()` y `estado = 'PENDIENTE'`
- El selector de contexto multi-copropiedad se construye como pantalla intermedia post-autenticación — no como modal sobre el dashboard. La URL debe cambiar para reflejar el contexto activo (ej. `/app/{copropiedad_slug}/dashboard`)
- La copia de roles entre copropiedades replica registros en `rol` y `rol_permiso` — son entidades independientes, sin FK al origen excepto `copiado_de_rol_id` informativo
- Los permisos del rol Administrador para "Gestionar usuarios y roles" no deben ser desactivables — es el único rol que siempre conserva este permiso de forma irrevocable
- Dejar punto de extensión en la evaluación de permisos para que en Fase 3 el módulo T.1 IA Asistente pueda sugerir ajustes de roles basándose en patrones de uso
