## 1. Descripción general

El módulo de Presupuesto, Cuotas y Pagos es el motor financiero operativo de cada copropiedad en PropIA. Gestiona el ciclo completo del presupuesto anual — desde su elaboración hasta su cierre de vigencia — incluyendo la liquidación automática de cuotas por unidad, el recaudo en línea vía pasarela de pagos y el seguimiento opcional de ejecución presupuestal.

No es un módulo contable. PropIA no reemplaza al software contable externo (Siigo, Alegra, World Office) — se integra con él en una fase posterior. Este módulo gestiona la dimensión **operativa** del presupuesto: qué se planea gastar, cómo se distribuye entre las unidades, cómo se recauda y cómo se ejecuta. Es el puente entre el presupuesto aprobado en asamblea y la realidad del día a día de la copropiedad.

**Principios de diseño que rigen este módulo:**
- Self-service 100% — el Administrador configura y opera sin intervención de A&D GROUP
- Zero-touch operativo — A&D GROUP no toca datos financieros de ningún tenant
- Tan fácil o más fácil que Excel — el editor de presupuesto debe reducir fricción, no aumentarla
- Flexibilidad configurable — cada funcionalidad avanzada es opcional; el admin activa lo que necesita
- Trazabilidad completa — cada cambio queda registrado con usuario, fecha y valor anterior
- Arquitectura abierta — diseñada para integración contable futura sin rediseño del módulo

## 4. Ciclo de vida del presupuesto

```
┌─────────────┐    ┌──────────────────┐    ┌───────────┐    ┌─────────────┐    ┌────────┐
│  BORRADOR   │───▶│  EN APROBACIÓN   │───▶│ APROBADO  │───▶│ EN EJECUCIÓN│───▶│ CERRADO│
│             │    │                  │    │           │    │             │    │        │
│ Admin edita │    │ Sometido a       │    │ Listo para│    │ Vigencia    │    │ Cierre │
│ libremente  │    │ asamblea (2.8)   │    │ liquidar  │    │ activa      │    │ formal │
│             │    │ o aprobado       │    │ cuotas    │    │             │    │ o dejar│
│             │    │ manualmente      │    │           │    │             │    │ abierto│
└─────────────┘    └──────────────────┘    └───────────┘    └─────────────┘    └────────┘
```

**Reglas de transición de estados:**

| Transición | Condición | Quién la ejecuta |
|-----------|-----------|-----------------|
| Borrador → En aprobación | Admin envía a asamblea (2.8) o marca como "en aprobación" | Administrador |
| En aprobación → Aprobado | Aprobación formal en asamblea (2.8) o aprobación manual con acta adjunta | Administrador |
| Aprobado → En ejecución | Admin activa la vigencia y el motor de liquidación | Administrador |
| En ejecución → Cerrado | Cierre de vigencia (flexible — formal o informal) | Administrador |

**Notas:**
- Solo puede haber **una vigencia En ejecución** a la vez.
- Un presupuesto en estado **Borrador** puede ser eliminado. A partir de **En aprobación**, solo puede ser archivado con trazabilidad.
- El historial de todas las vigencias es navegable desde el módulo.

## 5. Editor de Presupuesto

### 5.1 Principio de diseño

> El editor debe ser tan fácil o más fácil de usar que Excel. El admin no parte de cero — PropIA entrega una estructura base sugerida, lista para ajustar. Los cálculos son automáticos y en tiempo real. Las validaciones normativas son advertencias suaves, no bloqueos.

### 5.2 Rubros presupuestales

**Estructura base sugerida (precargada por PropIA):**

| Rubro | Tipo | Obligatorio | Editable |
|-------|------|-------------|---------|
| Administración general | Ordinario | No | Sí |
| Personal y nómina | Ordinario | No | Sí |
| Seguridad y vigilancia | Ordinario | No | Sí |
| Mantenimiento de zonas comunes | Ordinario | No | Sí |
| Servicios públicos comunes | Ordinario | No | Sí |
| Seguros | Ordinario | No | Sí |
| Aseo y jardinería | Ordinario | No | Sí |
| Gastos administrativos | Ordinario | No | Sí |
| **Fondo de imprevistos** | **Ordinario** | **Sí — no eliminable** | Solo monto |
| Otros gastos | Ordinario | No | Sí |

**Reglas del catálogo de rubros:**
- El admin puede agregar rubros personalizados ilimitados.
- El admin puede desactivar cualquier rubro del catálogo base, excepto el Fondo de Imprevistos.
- El admin puede renombrar los rubros del catálogo base.
- Los rubros inactivos no participan en el cálculo del presupuesto total ni de las cuotas.
- El Fondo de Imprevistos debe representar mínimo el **1% del presupuesto total** (Art. 39, Ley 675). PropIA muestra una advertencia suave si el monto está por debajo — no bloquea el guardado.

### 5.3 Capacidades del editor

| Capacidad | Descripción |
|-----------|-------------|
| **Edición inline** | El admin edita directamente en la tabla — sin formularios ni modales intermedios |
| **Cálculo en tiempo real** | Al modificar cualquier valor, el presupuesto total y la cuota proyectada por unidad se recalculan instantáneamente |
| **Vista dual** | El admin puede alternar entre vista de rubros (tabla de gastos) y vista de cuota proyectada por unidad (impacto real por unidad privada) |
| **Importación desde Excel** | El admin puede importar un presupuesto existente desde un archivo .xlsx o .csv. PropIA mapea las columnas y permite corregir antes de confirmar |
| **Anotaciones por rubro** | Cada rubro puede tener una nota de justificación interna (no visible para el residente) |
| **Vigencia configurable** | El admin define fecha de inicio y fin de la vigencia (no necesariamente enero–diciembre) |

### 5.4 Compartir borrador con el Consejo

Desde el estado **Borrador**, el admin puede compartir el presupuesto con los miembros del Consejo de Administración registrados en 2.3 (Gobierno):

- Botón **"Compartir con el Consejo"** visible solo en estado Borrador.
- PropIA notifica a cada consejero vía **email y WhatsApp** con un enlace de solo lectura.
- La vista compartida muestra el presupuesto completo con el desglose por rubro y la cuota proyectada por tipo de unidad.
- El consejero no puede editar — solo consultar.
- El admin puede revocar el enlace compartido en cualquier momento.

## 6. Cuotas Extraordinarias

Las cuotas extraordinarias son cobros adicionales al presupuesto ordinario, aprobados en asamblea, con un propósito específico y forma de recaudo definida.

### 6.1 Atributos de una cuota extraordinaria

| Atributo | Descripción | Obligatorio |
|----------|-------------|------------|
| Nombre | Nombre descriptivo de la cuota (ej: "Impermeabilización cubierta") | Sí |
| Propósito / uso | Descripción del destino del dinero | Sí |
| Monto total a recaudar | Valor total aprobado | Sí |
| Forma de recaudo | Cuota única, cuotas mensuales, número de cuotas | Sí |
| Base de liquidación | Coeficiente, cuota fija por tipo de unidad, o mixto | Sí |
| Vinculación a proyecto | Proyecto en módulo 2.10 al que se amarra la ejecución | Opcional |
| Aprobación | Vía asamblea formal (2.8) o manual con acta adjunta | Sí |
| Documento de aprobación | Acta de asamblea o punto del acta donde se aprobó | Recomendado |
| Fecha de inicio de recaudo | | Sí |
| Fecha de cierre de recaudo | | Opcional |

### 6.2 Reglas de cuotas extraordinarias

- Una copropiedad puede tener múltiples cuotas extraordinarias activas simultáneamente.
- Cada cuota extraordinaria tiene su propio ciclo: **Pendiente de aprobación → Aprobada → En recaudo → Cerrada**.
- El residente ve en su sesión las cuotas extraordinarias activas desglosadas por separado — nunca mezcladas con la cuota ordinaria.
- La ejecución del gasto asociado a una cuota extraordinaria puede vincularse a un proyecto en el módulo 2.10 para trazabilidad completa ante el consejo y la asamblea.
- PropIA genera un informe de estado por cuota extraordinaria: recaudado vs. meta, gasto ejecutado vs. recaudado.

## 7. Motor de Liquidación

### 7.1 Bases de liquidación soportadas

| Base | Descripción | Caso de uso típico |
|------|-------------|-------------------|
| **Coeficiente puro** | La cuota se calcula proporcionalmente al coeficiente de copropiedad de cada unidad | Administración general, seguros, zonas comunes |
| **Cuota fija por tipo de unidad** | Todas las unidades de un mismo tipo pagan el mismo valor, independiente del coeficiente | Parqueaderos, bodegas, locales |
| **Mixto por rubro** | Algunos rubros van por coeficiente, otros por cuota fija por tipo | Copropiedades con estructura heterogénea |

**Regla:** La base de liquidación se configura **por rubro**, no para todo el presupuesto. Esto permite que en un mismo presupuesto, la administración general vaya por coeficiente y los parqueaderos paguen una cuota fija.

### 7.2 Proceso de liquidación mensual

```
1. El motor toma el presupuesto total aprobado y lo divide en 12 (o el número de meses de la vigencia).
2. Para cada rubro, aplica la base de liquidación configurada.
3. Calcula el monto por unidad privada.
4. Genera un snapshot inmutable de la liquidación: fecha, base de cálculo usada, coeficientes, monto por unidad.
5. Notifica al residente / propietario vía email y WhatsApp con el valor de su cuota y el desglose.
```

### 7.3 Inmutabilidad de liquidaciones

- Cada liquidación genera un **snapshot inmutable** — no se recalcula hacia atrás bajo ninguna circunstancia.
- Si el presupuesto es modificado después de liquidaciones ya emitidas (por ejemplo, corrección aprobada en asamblea extraordinaria), el sistema **alerta al administrador** sobre las cuotas liquidadas bajo el presupuesto anterior.
- La reliquidación es siempre **manual** — el administrador la inicia explícitamente. El sistema nunca modifica cobros emitidos sin acción explícita.
- El historial de snapshots de liquidación es consultable y auditable.

## 8. Ejecución Presupuestal (opcional)

Este componente es **opcional**. El administrador lo activa si desea llevar el seguimiento operativo del gasto dentro de PropIA. Si no lo activa, el módulo funciona completamente para presupuesto, liquidación y recaudo.

### 8.1 Estructura por rubro

| Concepto | Descripción |
|----------|-------------|
| **Presupuestado** | Monto aprobado en asamblea para este rubro en la vigencia |
| **Comprometido** | Suma de valores estimados de tareas y proyectos vinculados a este rubro en 2.10 |
| **Ejecutado** | Suma de gastos registrados manualmente por el administrador |
| **Disponible** | Presupuestado − Comprometido − Ejecutado |

### 8.2 Registro de gasto

- El administrador registra un gasto indicando: rubro, monto, fecha, descripción y soporte adjunto (opcional).
- El soporte puede ser una factura, cotización, contrato o cualquier documento.
- Cada registro queda trazado con usuario y fecha.
- El registro de gasto **no reemplaza la contabilidad** — es un seguimiento operativo paralelo.

### 8.3 Vinculación con módulo 2.10

- Cualquier tarea o proyecto en 2.10 puede vincularse a un rubro del presupuesto.
- El valor estimado de la tarea/proyecto se refleja automáticamente como **Comprometido** en el rubro correspondiente.
- Cuando el administrador registra el gasto real, el sistema actualiza el **Ejecutado** y libera el Comprometido.

### 8.4 Informes de ejecución

- El módulo genera automáticamente el **Informe de Ejecución Presupuestal** por vigencia, con detalle por rubro.
- Este informe puede ser presentado al consejo o a la asamblea directamente desde PropIA.
- El informe incluye: presupuestado, comprometido, ejecutado, disponible, % de ejecución y documentos soporte adjuntos.

## 9. Panel de Recaudo

Vista global del estado del recaudo para el administrador. No es el estado de cuenta por unidad — ese vive en el módulo 2.7.

### 9.1 Métricas principales

| Métrica | Descripción |
|---------|-------------|
| **Esperado del mes** | Total de cuotas liquidadas para el período en curso |
| **Recibido** | Total de pagos confirmados en el período |
| **Pendiente** | Esperado − Recibido |
| **% de recaudo** | Recibido / Esperado × 100 |

### 9.2 Vista por unidad

- Lista de unidades con su estado de pago del período: Pagado / Pendiente / Vencido.
- Filtros por estado, tipo de unidad, torre/bloque.
- Acceso directo a la ficha de la unidad en 2.3 y al estado de cuenta en 2.7.

### 9.3 Registro manual de pagos

Para pagos por fuera de la pasarela digital (consignación bancaria, efectivo en portería):
- El administrador registra el pago indicando: unidad, monto, fecha, medio de pago y referencia.
- El pago manual queda marcado como **"Registrado manualmente"** con trazabilidad del usuario que lo registró.
- El sistema no valida la veracidad del pago manual — es responsabilidad del administrador.

## 10. Pasarela de Pagos — Wompi

### 10.1 Modelo de integración

PropIA integra Wompi bajo el modelo de **cuenta independiente por copropiedad**:

- Cada copropiedad crea su propia cuenta de comercio en Wompi.
- PropIA se conecta vía API keys configuradas por el administrador dentro del módulo.
- El dinero de los pagos va **directamente** a la cuenta bancaria de la copropiedad — PropIA nunca intermedia fondos.
- Las API keys se almacenan **cifradas por tenant** en la base de datos de PropIA.

### 10.2 Canales de pago soportados (Wompi)

| Canal | Disponibilidad |
|-------|---------------|
| PSE | ✅ Desde el inicio |
| Tarjeta débito | ✅ Desde el inicio |
| Tarjeta crédito | ✅ Desde el inicio |
| Nequi | ✅ Desde el inicio (nativo en Wompi) |
| Efectivo (Corresponsal) | ✅ Desde el inicio (Bancolombia a la mano) |

### 10.3 Configuración de costos bancarios

Cada copropiedad configura quién asume el costo de la transacción:

| Opción | Descripción |
|--------|-------------|
| **La copropiedad absorbe el costo** | El residente paga exactamente el valor de su cuota |
| **El residente asume el costo** | El sistema suma el costo de la transacción al valor a pagar en el momento del checkout |

Esta configuración es por copropiedad y puede modificarse en cualquier momento.

### 10.4 Procesamiento de pagos

- Las confirmaciones de pago de Wompi se procesan vía **webhooks** de forma asíncrona.
- El estado del pago se actualiza en background — sin bloquear la experiencia del residente.
- En caso de fallo en el webhook, el sistema reintenta automáticamente con backoff exponencial.
- El administrador puede consultar el log de transacciones y reconciliar manualmente si es necesario.

### 10.5 Activación guiada de Wompi

El flujo de activación de la pasarela es un asistente paso a paso dentro del módulo — no un formulario técnico con API keys en crudo:

```
Paso 1: ¿Ya tienes cuenta en Wompi? → [Sí, tengo cuenta] / [Necesito crearla]
Paso 2: Ingresa tus credenciales de Wompi (Public Key + Private Key)
         PropIA valida la conexión en tiempo real
Paso 3: Configura quién asume los costos de transacción
Paso 4: Define el nombre que verá el residente en el recibo de pago
Paso 5: Realiza un pago de prueba (opcional pero recomendado)
Paso 6: ✅ Pasarela activa
```

### 10.6 Integración futura — Go de AV Villas

> **Nota de arquitectura:** La integración con el sistema Go de AV Villas (banco AV Villas) está reservada como integración estratégica de alta prioridad. AV Villas tiene alta penetración en el mercado de PH colombiana y su sistema permite que los pagos queden aplicados automáticamente sin conciliación manual — lo que eliminaría uno de los principales dolores operativos del administrador.
>
> La arquitectura del módulo contempla una **capa de abstracción de pagos** que hoy apunta a Wompi y puede extenderse a Go de AV Villas u otras pasarelas sin rediseñar el módulo. Esta integración se activará una vez se tenga acceso a la documentación de la API de Go.

## 12. Aprobación del presupuesto

### 12.1 Flujo formal vía Asamblea (módulo 2.8)

```
Admin elabora presupuesto en 2.6
        ↓
Admin lo incluye como punto del orden del día en una asamblea en 2.8
        ↓
En la asamblea, se vota el presupuesto (módulo 2.8 gestiona la votación)
        ↓
Asamblea aprueba → 2.8 notifica a 2.6 → Presupuesto cambia a estado "Aprobado"
        ↓
Admin activa la vigencia en 2.6 → Estado "En ejecución"
```

### 12.2 Aprobación manual (presupuesto ya aprobado antes de PropIA)

Para copropiedades que llegan a PropIA con un presupuesto ya aprobado en asamblea:

1. El admin marca el presupuesto como **"Aprobado manualmente"**.
2. El sistema solicita adjuntar el acta de asamblea o el punto del acta donde consta la aprobación.
3. El documento adjunto queda vinculado al presupuesto como soporte de auditoría.
4. PropIA registra en el log: quién aprobó manualmente, fecha y documento adjunto.

**Misma lógica aplica para cuotas extraordinarias** — flujo formal vía 2.8 o aprobación manual con acta adjunta.

## 13. Cierre de vigencia

El cierre de vigencia es **flexible** — el admin decide si lo hace formalmente o simplemente abre una nueva vigencia dejando la anterior como referencia histórica.

### 13.1 Checklist guiado de cierre (opcional)

PropIA presenta un checklist al final de la vigencia:

| Ítem | Descripción | Acción |
|------|-------------|--------|
| Cuotas pendientes | Unidades con pagos sin confirmar | Ver lista / ignorar |
| Rubros con saldo disponible | Rubros con menos del 100% ejecutado | Trasladar a fondo de imprevistos / dejar como está / registrar devolución |
| Ejecución de cuotas extraordinarias | Estado de recaudo y gasto de cada cuota extraordinaria activa | Cerrar / mantener activa |
| Informe de cierre | Informe de ejecución presupuestal de la vigencia completa | Generar / omitir |

### 13.2 Traslado de saldos

El admin puede trasladar saldos no ejecutados a:
- El **Fondo de Imprevistos** de la siguiente vigencia.
- Un rubro específico de la siguiente vigencia.
- Dejarlo registrado como **saldo a favor de la copropiedad** sin traslado.

## 14. Integración Contable (fase posterior)

> Esta funcionalidad está completamente diseñada en este documento pero su implementación es posterior al lanzamiento del módulo. La arquitectura del módulo es abierta desde el inicio para soportarla sin rediseño.

### 14.1 Alcance de la integración

| Software | Estado |
|---------|--------|
| Siigo | Integración futura |
| Alegra | Integración futura |
| World Office | Integración futura |

### 14.2 Datos que PropIA enviará al software contable

| Evento | Datos a enviar |
|--------|---------------|
| Liquidación de cuota | Período, unidad, monto, rubro, base de cálculo |
| Pago recibido | Fecha, unidad, monto, canal de pago, referencia de transacción |
| Registro de gasto (ejecución) | Fecha, rubro, monto, descripción, soporte adjunto |
| Cuota extraordinaria | Nombre, monto total, forma de recaudo, pagos recibidos |

### 14.3 Contrato de datos

El mapeo de rubros de PropIA a cuentas contables del PUC (Plan Único de Cuentas) se configurará por copropiedad dentro del software contable de destino. PropIA enviará los datos estructurados — el mapeo contable es responsabilidad del contador y del software externo.

### 14.4 Modelo de integración técnica

- Autenticación por API keys del software contable externo, configuradas por copropiedad.
- Envío de eventos vía webhooks o polling según las capacidades de cada software.
- Log de sincronización por copropiedad — el admin puede ver qué se envió, cuándo y si hubo errores.
- Reintento automático en caso de fallo de sincronización.

| Saldo de rubro por debajo del mínimo normativo (Fondo de Imprevistos) | Email | Administrador |
| Cierre de vigencia próximo (30 días antes) | Email | Administrador |

## 16. Reglas de negocio

| # | Regla |
|---|-------|
| RN-01 | Solo puede existir una vigencia presupuestal en estado "En ejecución" simultáneamente |
| RN-02 | El Fondo de Imprevistos es un rubro obligatorio no eliminable. PropIA advierte si su monto es inferior al 1% del presupuesto total (Art. 39, Ley 675) |
| RN-03 | Un presupuesto en estado Borrador puede eliminarse. A partir de "En aprobación", solo puede archivarse con trazabilidad |
| RN-04 | Cada liquidación genera un snapshot inmutable. No se recalculan liquidaciones pasadas |
| RN-05 | La reliquidación siempre es manual — el sistema alerta pero nunca modifica cobros emitidos sin acción explícita del administrador |
| RN-06 | Las cuotas extraordinarias son independientes del presupuesto ordinario — se liquidan y recaudan por separado |
| RN-07 | Las cuotas extraordinarias requieren soporte de aprobación (acta de asamblea) — vía 2.8 o adjunto manual |
| RN-08 | El dinero de los pagos va directamente a la cuenta bancaria de la copropiedad — PropIA nunca intermedia fondos |
| RN-09 | Las API keys de Wompi se almacenan cifradas por tenant |
| RN-10 | Los pagos manuales quedan marcados como "Registrado manualmente" con trazabilidad del usuario |
| RN-11 | El borrador compartido con el Consejo es de solo lectura — los consejeros no pueden editar |
| RN-12 | Todo cambio en presupuesto, cuota o ejecución queda registrado en el log de auditoría con usuario, fecha y valor anterior |
| RN-13 | La ejecución presupuestal es completamente opcional — su activación no afecta las demás funciones del módulo |
| RN-14 | La base de liquidación se configura por rubro — no para el presupuesto completo |
| RN-15 | La integración contable es opcional y de activación posterior — su ausencia no limita ninguna funcionalidad del módulo |

## 17. Validaciones

| Campo / Acción | Validación |
|----------------|-----------|
| Monto del Fondo de Imprevistos | Advertencia suave si < 1% del total del presupuesto |
| Activación de vigencia | Solo si el presupuesto está en estado "Aprobado" |
| Cuota extraordinaria sin soporte | Advertencia al guardar — permite continuar con confirmación |
| Importación desde Excel | PropIA valida estructura de columnas antes de importar — muestra previsualización con errores detectados |
| API keys de Wompi | Validación de conexión en tiempo real al configurar |
| Reliquidación | El sistema requiere confirmación explícita del administrador antes de ejecutar |
| Cierre de vigencia con cuotas pendientes | El sistema advierte cuántas unidades tienen pagos sin confirmar — el admin decide continuar |

## 22. Notas para el desarrollador

1. **Capa de abstracción de pagos:** Implementar desde el inicio una interfaz `IPasarelaPagos` con métodos `iniciarPago()`, `confirmarPago()`, `consultarEstado()`. La implementación concreta de Wompi implementa esta interfaz. Cuando se integre Go de AV Villas u otra pasarela, se agrega una nueva implementación sin modificar el módulo.

2. **Snapshots de liquidación:** El campo `snapshot_calculo` en la tabla `liquidaciones` debe ser un objeto JSON que capture el estado exacto al momento del cálculo: coeficientes de cada unidad, base de liquidación de cada rubro, monto del presupuesto total, fecha de vigencia. Este snapshot es el soporte de auditoría ante cualquier discrepancia futura.

3. **Webhooks de Wompi:** Implementar un endpoint dedicado para recibir notificaciones de Wompi con verificación de firma HMAC. El procesamiento debe ser asíncrono (cola de tareas) — el webhook debe responder HTTP 200 inmediatamente y encolar el procesamiento.

4. **Cifrado de API keys:** Las credenciales de Wompi (`public_key_encrypted`, `private_key_encrypted`) deben cifrarse con una clave maestra por tenant usando AES-256. Nunca exponer las claves privadas al frontend.

5. **Motor de liquidación:** Implementar como un servicio aislado que recibe `presupuesto_id` + `periodo` y produce los registros en `liquidaciones` y `liquidaciones_unidades`. Debe ser idempotente — ejecutar dos veces el mismo período no debe generar duplicados.

6. **Cálculo de "Comprometido":** El valor comprometido por rubro se calcula en tiempo real sumando los valores estimados de las tareas/proyectos activos vinculados al rubro en el módulo 2.10. No se almacena — se consulta al vuelo para evitar inconsistencias.

7. **Integración contable futura:** Diseñar desde ahora los eventos de dominio que se emitirán hacia el software contable: `CuotaLiquidada`, `PagoConfirmado`, `GastoRegistrado`, `CuotaExtraordinariaAprobada`. Estos eventos se publicarán a una cola cuando la integración esté activa.

8. **Vista del residente:** El flujo de pago (3 pasos) debe estar optimizado para mobile-first. El desglose de la cuota es un acordeón colapsado por defecto — disponible bajo demanda.

9. **Multi-vigencia:** El sistema debe soportar consulta de vigencias anteriores sin afectar el rendimiento de la vigencia activa. Considerar particionamiento de tablas por `copropiedad_id` + año de vigencia si el volumen lo justifica.

10. **Importación desde Excel:** El parser de importación debe ser tolerante a variaciones de formato. Implementar en dos fases: (1) detección de columnas con confirmación del usuario, (2) importación con reporte de filas con error y filas exitosas.
