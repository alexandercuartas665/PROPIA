## 1. Descripción general

El módulo de Cartera y Estado de Cuenta es el motor de gestión de mora de cada copropiedad en PropIA. Gestiona el ciclo completo de la deuda por unidad privada — desde la primera cuota impaga hasta el cobro jurídico — incluyendo el cálculo de intereses, los acuerdos de pago formales, la condonación de deuda, la emisión de paz y salvos y el estado de cuenta en tiempo real para el residente.

No es un módulo contable. PropIA no reemplaza al software contable externo (Siigo, Alegra, World Office). Este módulo gestiona la dimensión **operativa** de la cartera: quién debe, cuánto debe, desde cuándo, en qué estado de gestión se encuentra y cómo se está resolviendo.

Este módulo es consumidor directo del módulo 2.6 — las liquidaciones generadas allí son la fuente primaria de la deuda. Sin un presupuesto activo en 2.6, el módulo opera en modo informativo sin datos financieros.

**Principios de diseño que rigen este módulo:**
- Self-service 100% — el Administrador gestiona la cartera sin intervención de A&D GROUP
- Zero-touch operativo — A&D GROUP no toca datos financieros de ningún tenant
- Configurabilidad total — estados, tiempos, reglas de imputación, paz y salvo y cálculo de intereses son configurables por copropiedad
- Trazabilidad completa — cada cambio de estado, acuerdo, condonación o emisión de documento queda registrado con usuario, fecha y detalle
- Autoservicio del residente — el residente consulta su situación financiera sin necesidad de contactar al administrador
- Escalamiento asistido — el sistema alerta, el administrador decide

## 4. Ciclo de vida de una deuda

```
┌─────────────────────────────────────────────────────────────────────┐
│  Cuota liquidada (desde 2.6)                                        │
│         ↓                                                           │
│  ┌──────────────┐                                                   │
│  │  AL DÍA      │  Cuota pagada dentro del período de gracia        │
│  └──────────────┘                                                   │
│         ↓  (vence el período de gracia sin pago)                    │
│  ┌──────────────┐                                                   │
│  │  EN MORA     │  La cuota genera intereses. Inicia el aging       │
│  └──────────────┘                                                   │
│         ↓  (sistema alerta al admin al cumplir el tiempo config.)   │
│  ┌──────────────────┐                                               │
│  │  NOTIFICACIÓN    │  Admin enviá comunicación formal al deudor    │
│  └──────────────────┘                                               │
│         ↓  (admin mueve manualmente al cumplir el tiempo config.)   │
│  ┌──────────────────┐                                               │
│  │  PRE-JURÍDICO    │  Gestión intensiva antes de cobro legal       │
│  └──────────────────┘                                               │
│         ↓  (admin mueve manualmente al cumplir el tiempo config.)   │
│  ┌──────────────────┐                                               │
│  │  JURÍDICO        │  Proceso legal externo — PropIA registra      │
│  └──────────────────┘                                               │
│                                                                     │
│  En cualquier estado: Acuerdo de Pago → Condonación → Pago total   │
└─────────────────────────────────────────────────────────────────────┘
```

**Notas sobre el ciclo:**
- Los estados de gestión son **configurables por copropiedad** — la PH puede renombrarlos, desactivar algunos o agregar estados intermedios.
- El escalamiento entre estados es **manual con alerta** — el sistema notifica al administrador cuando se cumple el tiempo configurado, pero nunca mueve el estado automáticamente.
- Una unidad puede tener deudas en diferentes estados simultáneamente (cuotas de distintos períodos).
- El estado de gestión se asigna a la **unidad**, no a una cuota individual — refleja la relación de cobro global con esa unidad.

## 7. Cálculo de Intereses de Mora

### 7.1 Modos de cálculo (configurable por copropiedad)

| Modo | Descripción | Defecto |
|------|-------------|---------|
| **Por cuota individual** | Cada cuota genera intereses desde su propia fecha de vencimiento. Es el método estándar en PH colombiana y el más defendible legalmente | ✅ Sí |
| **Por saldo total** | Los intereses se calculan sobre el saldo vencido acumulado total — útil para PHs que prefieren simplificar | No |

### 7.2 Tasa de mora

La tasa de mora se configura en el módulo 2.3 (Sección Finanzas):
- **Tasa legal vigente automática:** actualizada desde la Superfinanciera — PropIA la consume vía integración.
- **Tasa fija:** definida por el administrador, con validación de que no supere el máximo legal.

### 7.3 Motor de cálculo

- El motor de cálculo de intereses corre como **job nocturno** — actualiza el acumulado de intereses de cada cuota impaga.
- El capital original de la cuota es **inmutable** — los intereses se acumulan en un campo separado (`interes_acumulado`).
- El historial de cálculo diario es auditable.
- El período de gracia configurado en 2.3 determina desde cuándo empieza a contar la mora.

## 8. Imputación de Pagos

### 8.1 Regla de imputación (configurable por copropiedad)

| Opción | Descripción | Defecto |
|--------|-------------|---------|
| **Intereses → Capital más antiguo** | Se pagan primero los intereses acumulados, luego el capital de la cuota más antigua | ✅ Sí |
| **Capital más antiguo → Intereses** | Se paga el capital de las cuotas más antiguas primero, luego los intereses | No |
| **Distribución proporcional** | El pago se distribuye proporcionalmente entre capital e intereses de todas las cuotas impagas | No |

### 8.2 Proceso de imputación

La lógica de imputación se ejecuta **en tiempo real** al momento de registrar el pago:

```
1. El pago llega (desde Wompi o registro manual)
2. El motor aplica la regla de imputación configurada
3. Se actualiza el saldo de cada cuota afectada
4. Se genera el detalle de imputación (qué monto fue a qué cuota y concepto)
5. Se actualiza el estado de la unidad en el tablero
6. Se notifica al residente con el detalle de la imputación
```

El detalle de imputación es visible tanto para el administrador como para el residente en su estado de cuenta.

### 9.1 Ciclo de vida de un acuerdo

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  BORRADOR    │───▶│  PENDIENTE   │───▶│  VIGENTE     │───▶│  COMPLETADO  │
│              │    │  ACEPTACIÓN  │    │              │    │              │
│ Admin define │    │ Propietario  │    │ Cuotas al día│    │ Deuda saldada│
│ condiciones  │    │ debe aceptar │    │              │    │              │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
                                               │
                                               ▼
                                        ┌──────────────┐
                                        │  INCUMPLIDO  │
                                        │              │
                                        │ Cuota vencida│
                                        │ sin pago     │
                                        └──────────────┘
                                               │
                                               ▼
                                     Admin decide: renegociar
                                     o retomar cobro normal
```

### 9.2 Creación de un acuerdo de pago (wizard)

**Paso 1 — Definir condiciones:**

| Campo | Descripción | Obligatorio |
|-------|-------------|------------|
| Deuda incluida | Selección de cuotas/períodos que cubre el acuerdo | Sí |
| Monto total del acuerdo | Capital + intereses incluidos | Sí (calculado automático) |
| Número de cuotas | Cantidad de pagos del acuerdo | Sí |
| Valor por cuota | Calculado automáticamente — editable si hay distribución irregular | Sí |
| Fecha de primera cuota | | Sí |
| Condonación parcial de intereses | Porcentaje o monto condonado como incentivo (opcional) | No |
| Notas internas | Observaciones del administrador | No |

**Paso 2 — Previsualización del cronograma:**

| # Cuota | Fecha | Monto | Capital | Interés |
|---------|-------|-------|---------|---------|
| 1 | 05 Abr 2026 | $145.367 | $139.233 | $6.134 |
| 2 | 05 May 2026 | $145.367 | $140.688 | $4.679 |
| 3 | 05 Jun 2026 | $145.366 | $142.179 | $3.187 |
| **Total** | | **$436.100** | **$422.100** | **$14.000** |

**Paso 3 — Aceptación formal del propietario:**

El acuerdo no entra en vigor hasta que el propietario lo acepte formalmente:

- PropIA envía al propietario un **enlace de aceptación** por email y WhatsApp.
- El propietario ingresa a la plataforma (o al enlace seguro) y revisa el cronograma completo.
- Al aceptar, el sistema genera un **registro de aceptación inmutable** con:
  - Hash del documento de acuerdo
  - Timestamp de aceptación (servidor)
  - ID del usuario aceptante
  - IP de origen
  - Método de autenticación usado
- El administrador recibe notificación de aceptación.
- El acuerdo pasa a estado **Vigente**.

### 9.3 Seguimiento de cuotas del acuerdo

- El motor de seguimiento evalúa diariamente el cumplimiento del acuerdo.
- Si una cuota del acuerdo vence sin pago, el sistema **alerta al administrador** y cambia el acuerdo a estado **Incumplido**.
- El administrador decide: renegociar el acuerdo (nuevo wizard) o retomar el cobro normal.
- Al renegociar, el acuerdo anterior queda en el historial con trazabilidad completa — no se elimina.
- Los pagos de cuotas del acuerdo se registran por la misma vía que los pagos normales (Wompi o manual).

### 9.4 Reglas de negocio de acuerdos

| # | Regla |
|---|-------|
| AC-01 | Solo puede existir un acuerdo **Vigente** simultáneamente por unidad |
| AC-02 | Un acuerdo en estado Borrador puede eliminarse sin trazabilidad |
| AC-03 | A partir de Pendiente de Aceptación, el acuerdo no puede eliminarse — solo cancelarse con registro de motivo |
| AC-04 | La condonación parcial de intereses incluida en el acuerdo queda registrada como condonación en el historial de la unidad |
| AC-05 | El propietario tiene un plazo configurable para aceptar el acuerdo antes de que expire |
| AC-06 | Un acuerdo incumplido puede renegociarse ilimitadas veces — cada renegociación crea un nuevo acuerdo vinculado al anterior |

## 10. Condonación de Deuda

La condonación es la eliminación total o parcial de una deuda (capital y/o intereses) por decisión del administrador o de la asamblea.

### 10.1 Tipos de condonación

| Tipo | Descripción |
|------|-------------|
| **Condonación de intereses** | Se elimina el total o un porcentaje de los intereses acumulados — práctica habitual como incentivo de pago |
| **Condonación de capital** | Se elimina una parte del capital adeudado — requiere respaldo de decisión de asamblea |
| **Condonación total** | Se elimina la totalidad de la deuda (capital + intereses) |

### 10.2 Flujo de condonación

1. El administrador selecciona la deuda a condonar desde la ficha de la unidad.
2. Define el tipo de condonación, el monto y el motivo.
3. El sistema solicita confirmación explícita con resumen del impacto.
4. Opcionalmente, el administrador adjunta el acta o soporte de la decisión.
5. La condonación se aplica y queda registrada de forma **inmutable** en el historial.

### 10.3 Trazabilidad de condonaciones

Cada condonación registra:

| Campo | Descripción |
|-------|-------------|
| Usuario que autorizó | ID + nombre |
| Fecha y hora | Timestamp del servidor |
| Tipo | Intereses / Capital / Total |
| Monto condonado | Valor exacto |
| Motivo | Texto libre obligatorio |
| Documento soporte | Adjunto opcional |
| Saldo antes / después | Snapshot del estado de la deuda pre y post condonación |

## 11. Paz y Salvo

### 11.1 Tipos de paz y salvo

| Tipo | Condición de emisión | Descripción |
|------|---------------------|-------------|
| **Pleno** | Deuda total = $0 | La unidad no tiene ninguna obligación pendiente con la copropiedad |
| **Condicionado** | Acuerdo de pago vigente y al día | La unidad tiene deuda pero está cumpliendo un acuerdo formal. El documento especifica las condiciones |

### 11.2 Configuración del paz y salvo (por copropiedad)

| Parámetro | Opciones | Descripción |
|-----------|---------|-------------|
| **Emisión automática** | Habilitada / Deshabilitada | Si está habilitada, el sistema puede generar el paz y salvo automáticamente cuando se cumplen las condiciones. Requiere datos financieros activos en 2.6 | 
| **Paz y salvo condicionado** | Habilitado / Deshabilitado | Define si la PH acepta emitir paz y salvos a unidades con acuerdo vigente |
| **Solicitud por el residente** | Habilitada / Deshabilitada | Define si el residente puede solicitar su paz y salvo desde su sesión |
| **Validez del documento** | Días configurables | Cuántos días es válido el paz y salvo desde su emisión (ej: 30 días) |
| **Mensaje adicional** | Texto libre | Texto personalizable que aparece en todos los paz y salvos de la PH |

### 11.3 Condición de emisión automática

El paz y salvo automático solo está disponible cuando:
- Hay un presupuesto **En ejecución** en el módulo 2.6.
- Los pagos de la unidad están registrados en PropIA (vía Wompi o manual).
- El módulo 2.6 tiene liquidaciones generadas para los períodos correspondientes.

Si alguna de estas condiciones no se cumple, el sistema muestra un aviso al administrador indicando que la emisión automática no está disponible y permite la emisión manual con responsabilidad explícita del administrador.

### 11.4 Emisión manual

Cuando no hay datos financieros activos o el administrador decide emitir manualmente:
- El sistema muestra una advertencia: *"PropIA no puede verificar automáticamente el estado financiero de esta unidad. Al emitir este paz y salvo, usted asume la responsabilidad de la certificación."*
- El administrador confirma explícitamente.
- El paz y salvo emitido queda marcado como **"Emitido manualmente"** en el historial.

### 11.5 Solicitud por el residente

Si la configuración lo permite:
1. El residente solicita el paz y salvo desde su sesión.
2. Si las condiciones se cumplen (deuda cero o acuerdo al día) y la emisión automática está habilitada, el documento se genera de inmediato.
3. Si requiere revisión manual, el sistema notifica al administrador con la solicitud pendiente.
4. El administrador aprueba o rechaza con motivo.
5. El residente recibe el documento o la notificación de rechazo.

### 11.6 Documento de paz y salvo

Cada paz y salvo emitido es un documento PDF inmutable que incluye:

| Elemento | Descripción |
|----------|-------------|
| Encabezado de la copropiedad | Nombre, NIT, dirección, logo |

## 15. Comportamientos automáticos

| Trigger | Comportamiento |
|---------|---------------|
| Fin del período de gracia sin pago | La cuota pasa a estado "En mora". El sistema genera intereses desde ese día. Notificación automática al propietario |
| Job nocturno | Recalcula intereses acumulados de todas las cuotas impagas |
| Unidad cumple el tiempo configurado en un estado | Alerta al administrador en dashboard 2.2 y notificación — el estado NO cambia automáticamente |
| Cuota de acuerdo vence sin pago | Alerta al administrador. El acuerdo pasa a "Incumplido" |
| Deuda de una unidad llega a $0 | Estado de la unidad actualizado a "Al día". Si paz y salvo automático está habilitado y hay datos financieros activos, se genera y notifica |
| Pago recibido desde Wompi (webhook) | Imputación automática según regla configurada. Actualización de saldo. Notificación al residente con detalle de imputación |
| Pago manual registrado | Misma lógica que pago Wompi — imputación automática |

## 16. Reglas de negocio

| # | Regla |
|---|-------|
| RN-01 | La deuda pertenece a la **unidad privada**, no a la persona que la habita — consistente con Art. 30, Ley 675 |
| RN-02 | Sin presupuesto activo en 2.6, el módulo muestra estado "Sin datos financieros activos" — no bloquea la consulta de historial |
| RN-03 | El capital original de cada cuota es **inmutable** — los intereses se acumulan en campo separado |
| RN-04 | Los snapshots de liquidación de 2.6 no se recalculan desde 2.7 bajo ninguna circunstancia |
| RN-05 | El escalamiento de estado de gestión es siempre **manual** — el sistema alerta, nunca mueve el estado solo |
| RN-06 | Solo puede existir un acuerdo de pago **Vigente** simultáneamente por unidad |
| RN-07 | La aceptación del acuerdo de pago genera un registro inmutable con hash, timestamp, ID del aceptante e IP de origen |
| RN-08 | Los paz y salvos emitidos son documentos inmutables — no se editan, solo se anulan con trazabilidad |
| RN-09 | El paz y salvo automático requiere datos financieros activos en 2.6 — sin ellos, solo se puede emitir manualmente con responsabilidad explícita del administrador |
| RN-10 | Toda condonación queda registrada de forma inmutable con usuario, fecha, monto y motivo |
| RN-11 | La renegociación de un acuerdo crea un nuevo acuerdo vinculado al anterior — el historial nunca se elimina |
| RN-12 | Los pagos manuales quedan marcados como "Registrado manualmente" con trazabilidad del usuario |
| RN-13 | El residente solo tiene acceso a su propia información financiera — nunca a la de otras unidades |
| RN-14 | Todas las notificaciones de cartera pasan por el motor transversal de notificaciones — no lógica propia en este módulo |
| RN-15 | La imputación de pagos se ejecuta en tiempo real al momento del registro — no en batch |

## 17. Validaciones

| Campo / Acción | Validación |
|----------------|-----------|
| Emisión de paz y salvo automático sin datos en 2.6 | Bloqueo con advertencia explicativa — solo permite emisión manual con confirmación explícita |
| Cambio de estado de gestión | Requiere selección de motivo — campo obligatorio |
| Creación de acuerdo sin deuda registrada | Error bloqueante — no se puede crear un acuerdo sin deuda activa en el sistema |
| Condonación de capital | Advertencia fuerte: "Esta acción es irreversible. Se recomienda adjuntar el soporte de asamblea." |
| Acuerdo con monto total inferior a la deuda | Advertencia: "El acuerdo no cubre la totalidad de la deuda. La diferencia quedará como saldo pendiente." |
| Anulación de paz y salvo | Requiere motivo obligatorio — genera registro inmutable de la anulación |
| Plazo de aceptación del acuerdo vencido | El acuerdo pasa a estado Expirado — el admin debe crear uno nuevo |

## 21. Notas para el desarrollador

| Área | Nota |
|------|------|
| **Job nocturno de intereses** | Implementar como cron job que corra a las 00:05 hora Colombia (UTC-5). Debe ser idempotente — si corre dos veces el mismo día no debe duplicar intereses. Registrar en `interes_diario_log` con la tasa aplicada |
| **Evaluación de alertas de estado** | Job nocturno separado que evalúa `dias_en_mora` vs `dias_alerta` de cada estado. Si se cumple la condición, genera una alerta en el dashboard y una notificación al administrador |
| **Generación de PDF** | Server-side con soporte de gráficos (recharts o similar renderizado en servidor). Los PDFs se almacenan en storage por tenant y se entregan como URL firmada de tiempo limitado |
| **Hash de paz y salvo** | Generar SHA-256 del contenido del documento (unidad + propietario + tipo + fecha + condiciones + emisor). El código de verificación debe ser validable en una URL pública de PropIA sin requerir login |
| **Webhook Wompi** | El webhook de confirmación de pago de Wompi debe procesarse en 2.6. El resultado (pago confirmado + imputación) se comunica a 2.7 vía evento interno — no llamada directa |
| **Aceptación de acuerdo** | El enlace de aceptación debe ser un token de un solo uso con expiración configurable. Al acceder, mostrar el cronograma completo antes del botón de aceptación. Registrar todos los metadatos en el momento exacto del clic |
